1.0 Abstract & Executive Summary

Modern distributed computing environments demand instantaneous visibility into physical and virtual server infrastructure. Traditional monitoring architectures rely heavily on periodic REST or SNMP polling, introducing substantial HTTP handshaking overhead, database lock contention, and delayed anomaly detection. Furthermore, when infrastructure bottlenecks occur (such as memory leakage, thread starvation, or disk saturation), operations engineers are subjected to alert fatigue without actionable remediation context.

MonitorX resolves these limitations through a unified, event-driven infrastructure observability ecosystem designed and implemented for modern Linux and hybrid cloud topologies. The platform pairs high-frequency asynchronous hardware telemetry with an intelligent Autonomous AI Site Reliability Engineering (SRE) Copilot. Telemetry is collected every 2,000 milliseconds with minimal kernel footprint (~14ms execution time) and pushed across persistent full-duplex WebSockets directly to a GPU-accelerated React dashboard. In tandem, the AI SRE agent continuously correlates historical metrics, identifies resource saturation risks, computes a normalized 0–100 infrastructure health index, and outputs copyable, verified shell remediation playbooks.

Key Engineering Achievements
  • Sub-second latency (<4ms local, <35ms cloud) via Socket.IO bidirectional framing with zero client-side polling.
  • Tri-Engine Multi-Provider AI Architecture supporting Google Gemini 2.5 Flash, OpenAI GPT-4o-mini, and a fully offline deterministic heuristics engine.
  • Zero-maintenance bounded storage achieved via native MongoDB 24-hour Time-To-Live (TTL) auto-purging collections.
  • One-liner Linux deployment: Autonomous agent self-installs as a resilient, auto-restarting Systemd service via curl | bash.

2.0 Problem Statement & Motivation

Infrastructure monitoring historically suffers from three critical architectural shortcomings:

  1. High Overhead of Pull-Based Polling: Tools querying servers via HTTP REST polling initiate hundreds of TCP handshakes every minute, consuming CPU cycles that should be allocated to user workloads.
  2. Passive Data Without Actionability: Existing dashboards present graphs but leave root-cause diagnosis entirely to human operators, increasing Mean-Time-To-Resolution (MTTR) during outages.
  3. Complex Agent Provisioning: Enterprise monitoring agents (such as Prometheus node_exporter or Datadog) require complex configuration files, firewall routing, and significant background memory footprints.

MonitorX overcomes these hurdles by transforming server monitoring from a passive reporting utility into an active, self-diagnosing, autonomous SRE assistant.

4.0 Autonomous AI SRE Copilot & Diagnostics Engine

The standout innovation of MonitorX is its Autonomous Site Reliability Engineering (SRE) Copilot mounted under /api/ai and integrated directly across the dashboard.

To ensure 100% operational availability even during network disconnects or API quota limits, the AI module implements a 3-tier fallback architecture:

4.2 Remediation Playbook Generation

When an infrastructure threshold is breached, the AI engine outputs verified, non-destructive Linux terminal commands organized into: (1) Immediate Triage, (2) Deep Cleanup, and (3) Verification checks.

5.0 Backend Implementation & Telemetry Engine

The backend is built on Node.js using Express 5.2.1 and Socket.IO 4.8.3. Key engineering pillars include:

  • Hardware Introspection: Utilizes systeminformation to read CPU core clock frequencies, memory buffers, swap allocation, partition mount points, and network packet rates.
  • Heartbeat & Liveness Tracker: The server evaluates active agents; if an agent fails to send a push payload within 15,000 milliseconds, it is dynamically transitioned to offline and alerts are dispatched.
  • Security & Hardening: Includes helmet for HTTP security headers, express-rate-limit for endpoint protection, and Bcrypt password hashing.

6.0 Database Design & 24-Hour TTL Auto-Purge

A critical challenge in time-series telemetry is database storage exhaustion. At a 2-second sampling interval, a single server generates 43,200 metric records per day. MonitorX solves this using MongoDB Time-To-Live (TTL) indexing:

7.0 Frontend Engineering & Data Analytics

The frontend is implemented as an ultra-responsive React 18 SPA built with Vite 6:

  • Responsive Grid Sizing: Fixed prior layout blowouts by utilizing CSS Grid repeat(2, minmax(0, 1fr)) tracks with explicit min-width: 0 constraints.
  • High-Frequency Charts: Leverages Recharts AreaChart with custom SVG linear gradients, animated dots disabled for optimal 60 FPS performance, and dark frosted tooltips.
  • Global AI Copilot Drawer: Slide-over drawer triggerable from any screen via custom browser events (open-ai-drawer) with real-time telemetry pre-loaded into prompt contexts.

9.0 Review Committee Defense Q&A (Viva Guide)

Q1: Why did you choose WebSockets over traditional REST polling?

Answer: REST polling requires repeated TCP handshakes, TLS negotiations, and redundant HTTP header parsing every 2 seconds, which strains server resources. WebSockets maintain a single persistent TCP connection, pushing metric updates with sub-5ms latency and zero client-side request overhead.

Q2: How does the AI Copilot function when there is no internet connection?

Answer: MonitorX implements a tri-tier architecture with an offline Deterministic Heuristics Engine. If external LLM APIs (Gemini/OpenAI) are unavailable, the local engine calculates resource standard deviations, swappiness, and partition usage locally in ~18ms with zero network requests.

Q3: How do you prevent MongoDB from running out of storage over long running periods?

Answer: We implemented native MongoDB TTL collections via createdAt: { expires: 86400 }. MongoDB's background daemon automatically purges documents older than 24 hours, keeping storage permanently bounded under 50MB.

Q4: How do remote nodes communicate securely with the central monitoring server?

Answer: Remote agent daemons authenticate via secret token keys (x-agent-key header) over HTTPS. On the client side, dashboards use JSON Web Tokens (JWT) with bcrypt password hashing and rate limiting.

Q5: How did you fix the layout and Recharts grid resizing issue?

Answer: Recharts calculates SVG width from its parent element. Inside CSS grid containers without strict bounds, Recharts continuously expands tracks beyond the viewport. We resolved this by constraining columns with minmax(0, 1fr) and wrapping charts in containers with min-width: 0.
